# 分阶段设计与交付

版本：0.2.0。

使用用户的语言工作。遵循用户已有授权、仓库规范和适用的专项技能。不绑定语言、框架、行业或工具。

## 0. 先选模式并声明

开工前判断模式，并用一句话告诉用户："按 Lite/Standard/Full 模式，沟通方式为……"。用户可以随时改。拿不准时选高一档。

| 模式 | 适用 | 最小产物 | 阶段 |
|---|---|---|---|
| Lite | 单一目标；预计实现改动 ≤3 个文件且 ≤1 小时；无新架构决策；无不可逆操作 | 单份 `delivery-notes.md`（需求重述、验收项、问题与证据、结论） | 1 个，可不拆 |
| Standard | 多模块或多文件；需要拆成 2–4 个阶段 | 三份文档 | 2–4 个 |
| Full | 新项目；跨系统；涉及数据迁移、安全、支付、权限或对外发布 | 三份文档 + 设计确认关卡 + 高风险阶段独立复核 | 按需 |

**沟通方式**（开工时与模式一并声明，用户明确说了就照用户的）：
- 逐阶段确认：每阶段汇报后等用户答复再进入下一阶段。
- 连续执行：汇报后继续，仅在需要新的范围或取舍决定时暂停。
- 已有明确设计或连续执行授权时优先沿用，不重复确认。用户没说时的默认值：Full 为"设计确认后逐阶段确认"；Standard 为"设计确认一次后连续执行"；Lite 为连续执行。

**用户不在或没有答复时**：不要空等。记录当前假设，只做可回退且不依赖该决定的独立工作；决定项标为"待确认（暂按推荐方案）"；不进入依赖该决定的阶段，不执行不可逆操作。沉默不等于同意。

## 1. 重述需求

实施前先写"我理解你的需求是……"，覆盖：问题与目标用户、交付物、范围与明确不做的内容、约束、已明确的成功标准、未确定的关键点和假设。

不要把假设写成用户要求。先读已有资料；只询问会改变目标、架构、交付物或验收的缺失信息。信息充分时直接进入设计。

## 2. 设计并冻结验收基线

读取 [文档模板](references/document-templates.md) 建立文档；Lite 将设计、问题方案、报告、状态块合并在 delivery-notes.md，后续所有三文档指令均映射到此文件，不为 Lite 新建三份文档。Standard/Full 使用三份文档；已有同类文档时更新原文件。保存位置遵循用户指定和仓库规范；无写入能力时给出完整文本并说明未落盘。参考 [示例](references/example.md) 校准填写深度。

- 需求编号 R-001，验收项 AC-001，每条核心需求映射到交付物、阶段和验证方式。
- 验收标准必须可检查：操作、预期结果、阈值（适用时）、证据来源。没有依据时不要编造性能或安全阈值。
- 在设计文档中把每个阶段退出必须重跑的最小回归集标为 `smoke`。
- **验收标准在进入实施前冻结。** 之后任何修改都写进决策记录（来源、原因、影响），不能为了通过而改标准。
- 设计包含流程、模块与接口、数据或状态、关键选择与理由、失败路径、风险、实施与回退方式。非代码项目替换为内容结构、制作流程和检查方式。
- 按可独立演示和验证的交付物拆阶段，不为凑数制造阶段。每阶段写明目标、输入、任务、产物、依赖、退出标准。
- Full 模式：设计完成后展示并等待用户确认，再生成项目代码；若用户已明确授权设计和准备实施，沿用授权，只在尚未获授权的具体操作处暂停。

## 3. 阶段实施与自检

开始阶段时说明目标、验收项和计划检查。发现问题先记录，不无依据地扩大范围。

报告前完成适用的自检：对照需求与设计检查实现；运行仓库规定的构建、测试、lint、类型检查；覆盖失败路径、边界和并发；UI 或文档项目实际查看渲染与交互；核对与本任务相关的安全、性能、成本、数据完整性。

- **累积回归**：阶段退出前重跑前序阶段已 PASS 的 `smoke` 项，出现回归按新问题记录。
- 记录对象或版本、命令或操作、实际结果和日志摘要，保证别人能重跑。
- 状态只用 PASS / FAIL / BLOCKED / NOT RUN / N/A。静态阅读、跳过、没有工具都不算 PASS。构建成功不能替代相关测试。
- 优化有测量时给前后数据，没测量时只写预期收益。
- **独立复核**：Full 模式下涉及安全、数据迁移、支付、权限、对外发布的阶段，退出前交给未参与实现的审查者（子 Agent 或新会话）核对证据。做不到时自审并在报告中标明"未独立复核"。
- **检查点**：阶段通过后在报告记录可核验的产物版本（现有 commit SHA + 工作区差异，或文件 SHA-256）、验收证据位置和恢复步骤。默认不自动 commit、tag、push 或部署；仅在用户已有明确授权或仓库规范要求时创建对应版本记录，排除他人改动。无版本管理或禁止提交时用哈希清单与必要副本；副本必须避免被测试、构建或打包工具自动发现，不改变现有检查范围。创建后复验发现范围和测试计数。备份是恢复材料，不代替验收，也不等于已执行回退。
- **操作授权**：对删除数据、迁移、force push、部署、对外发送等操作，核对已有授权中的动作、对象、环境和范围。准备方案和 dry-run 的授权不等于实际执行授权；CLI 确认参数不等于用户同意。范围内已有明确授权时直接执行，不重复问；新增目标、范围或授权失效时先展示具体方案再沟通。未授权项保留。遵循运行环境对特定操作的确认规则，不将可回退的普通代码编辑一概视为不可逆。

### 问题分级

| 级别 | 含义 | 对推进的影响 |
|---|---|---|
| S0 阻断 | 数据丢失或损坏、安全漏洞、核心流程不可用、必需检查失败 | 阶段不得通过，依赖它的阶段不得开始 |
| S1 高 | 主要功能缺陷或明显回归，有绕行方式 | 阶段不得通过；用户可明确接受，接受后记录，检查状态仍为 FAIL |
| S2 中 | 次要缺陷，不影响验收 | 记录，可延期 |
| S3 低 | 体验、风格、文档瑕疵 | 记录 |

类型区分：**错误**（行为与预期不符且有复现）、**告警**（工具或运行时输出的警告）、**风险**（尚未发生的隐患）、**限制**（环境、权限、范围导致未做或未验）。项目有自己的分级约定时以约定为准。

## 4. 阶段汇报与沟通

阶段结束或被阻塞时，完整内容写入 `stage-report.md`（Lite 写入 delivery-notes.md），对话里给 15 行以内的短版。以下标签每项都保留，没有内容写“无/不适用”，不能靠文件链接省略：

1. **结论与状态**（通过 / 待沟通 / 修复中 / 阻塞，一句话理由）。
2. **需要你决定的事**（问题、推荐方案、必要替代方案、取舍）。没有则写"无"。
3. 做了什么、优化手段与代价、没做什么（各一两句，附文档位置）。
4. 告警与代码错误摘要（含编号、级别、证据位置）。未发现时写检查范围和"本轮检查未发现"，不宣称绝无错误。
5. 验收结果摘要（PASS/FAIL/BLOCKED 计数及未通过项）。

阶段状态只用：进行中、待沟通、修复中、通过、阻塞。实现结束不等于通过。

## 5. 把沟通结果写入优化设计并修复

每个问题编号 ISSUE-001，记录级别、类型、证据、复现、影响范围、根因（已验证或假设）、关联需求与验收项。

修改前先把方案写入 `optimization-design.md`（Lite 写入 delivery-notes.md）：变更点、替代方案、预期收益、风险、验证、回退，并标明决策来源（用户明确答复 / 此前授权覆盖 / 待用户决定）。不能把 Agent 的建议记成用户确认。

用户反馈到达后先更新决策和范围；涉及需求变化时同步更新设计文档、阶段依赖和验收基线，保留理由。禁止通过删测试、降阈值或移除原需求来掩盖失败。

修复循环：定位 → 记录方案 → 最小必要修复 → 重跑失败项和 smoke → 更新证据与状态 → 汇报。验证通过后才标记已修复，"代码已改未验证"保持待复验。同阶段内已授权的修复不需要逐次确认。

**无进展**指同一失败特征（同一检查、同一错误信息或同一未达标指标）连续三轮修复后仍然存在，或指标没有改善。每轮必须换新的假设，不能重复同一手段。达到时停止盲目重试，保存每轮证据，说明剩余障碍并给出替代方案，不宣称达标；拿到新信息后继续。

## 6. 最终验收与续接

只有核心需求可追溯、必需检查通过、S0 和 S1 问题已关闭（或 S1 已被用户明确接受并记录）、文档与产物一致时才报告交付通过。最终说明交付物、验收证据、仍有的限制和后续操作，不承诺绝对无错误或未经验证的生产可用性。

每次结束时更新当前模式文档顶部的**状态块**（当前阶段、未关闭问题、待决策、下一步）。续接时先读状态块和未关闭问题，再按需读细节，恢复已达成的决策和授权，不从头设计，也不重复索取。已关闭阶段的细节可以归档到文档末尾的"历史"部分。当前问题状态只保留一个权威字段；关闭后同步更新问题总表及状态块，旧状态标明为历史，不能同时写“待复验”和“已关闭”。状态块分别列未关闭阻断项与延期告警/风险；存在延期问题时不能笼统写“未关闭问题：无”。验收计数只统计当前结果，不把历史复现 FAIL 计为当前失败。
