# 分阶段设计与交付

使用用户的语言工作。按项目大小缩放文档与阶段数量，不绑定语言、框架、行业或特定工具。遵循用户已有授权、仓库规范和适用的专项技能。

## 1. 先重述需求

在实施或生成项目代码之前，先用简洁文字说明“我理解你的需求是……”，覆盖：
- 要解决的问题、目标用户和主要使用场景。
- 交付物、范围、明确不做的内容以及现有约束。
- 已明确的成功标准、尚未确定的关键点和当前假设。

不要把假设写成用户要求。先读取已有项目资料；只询问会改变目标、架构、交付物或验收的缺失信息。信息充分时直接完成设计，不为了重述需求另设确认关卡。若用户要求先确认设计再实施，则展示具体设计后等待其答复。

## 2. 设计并建立验收基线

读取 [文档模板](references/document-templates.md)，建立以下三个可持续更新的项目文档，已有同类文档时更新原文件而非制造副本：
- `project-design.md`：需求、方案、阶段计划及验收基线。
- `optimization-design.md`：问题证据、沟通决策、修复方案与复验记录。
- `stage-report.md`：每阶段的成果、限制、检查证据与当前状态。

把文档保存到用户指定位置；已有受版本管理的项目优先遵循其文档目录和命名。其他用户交付文件遵循运行环境的持久保存规则，不能只写在对话里而声称已经保存。无写入能力时提供完整文本并明确尚未落盘。

为需求分配稳定编号 R-001 等，为验收项分配 AC-001 等。将每条核心需求映射到交付物、所属阶段和验证方式。标准必须可检查：注明操作、预期结果、阈值（适用时）及证据来源；没有依据时不要编造性能或安全阈值。

设计包含业务流程、模块与接口、数据或状态、关键技术选择及其理由、失败路径、适用风险、实施与回退方式。非代码项目替换为对应的内容结构、制作流程及检查方式。仅在确实需要时调用其他技能生成效果图、原型或格式化文档。

按可独立演示和验证的交付物拆分阶段，通常为设计基线、核心流程、边界与可靠性、最终交付；根据项目调整，不能为了凑阶段制造工作。每阶段明确目标、输入、任务、产物、依赖、退出标准。小项目可合并阶段，但保留需求重述、设计、阶段汇报与验收闭环。

## 3. 按阶段实施与自检

开始阶段时说明目标、验收项和计划中的检查。执行当前阶段的必要工作；发现问题时记录，避免无依据扩大范围。

在报告前完成适用的自检：
- 对照需求和设计检查实现，审查改动和接口兼容性。
- 对代码项目运行相关构建、测试、lint、类型检查或其他仓库规定检查；按改动选择有意义的回归测试。
- 覆盖本阶段相关的失败路径、边界和并发问题；UI 或文档项目实际检查展示、交互或渲染结果。
- 核对安全、性能、成本、数据完整性等与当前任务相关的约束，不添加无关的检查清单。

记录检查对象/版本、命令或操作、实际结果和必要的日志摘要。区别 PASS、FAIL、BLOCKED、NOT RUN、N/A；跳过、没有工具或仅静态阅读均不算测试通过。优化结论有测量时给出前后证据，无测量时只描述预期收益。

## 4. 每阶段必须汇报并沟通

阶段实施结束或被阻塞时，更新 `stage-report.md`，同时向用户给出包含以下各项的阶段总结：
1. 做了什么：对应需求、交付物与可查看的位置。
2. 优化手段：具体措施、理由、实际效果及代价；没有优化则明确说明。
3. 没做什么：计划内未完成、主动延期、不在范围内的项目及影响。
4. 告警：实测告警、风险、环境限制、待验证项及严重度。
5. 代码错误：已修复和仍存在的错误、证据、影响与定位；非代码项目注明不适用并列出对应质量缺陷。未发现时写“本轮检查未发现”，不能宣称绝无错误。
6. 验收结果：每项状态、证据和阶段结论。
7. 方案与沟通：需要解决的问题、推荐方案、必要的替代方案、取舍和用户需决定的事项。

每阶段默认留下一个沟通节点，让用户能纠正范围、方案及风险处理。已有明确授权继续全部阶段时，向用户发出总结并继续，不重复索取同意；需要新的范围或取舍决定、或用户要求逐阶段确认时，完成所有独立工作后等待答复。用户没有回复不等于同意新方案。进行同阶段的已授权修复不要求逐次确认。

状态只用：进行中、待沟通、修复中、通过、阻塞。实现已结束不代表阶段通过。存在未解决的阻断项时报告“阻塞/修复中”，不能进入依赖其结果的后续阶段；独立工作可继续。

## 5. 把沟通结果写入优化设计并修复

为每个问题使用稳定编号 ISSUE-001 等，记录严重度、证据、复现方法、影响范围、根因（已验证或假设）、关联需求和验收项。

在修改前将方案写入 `optimization-design.md`，包含变更点、替代方案、预期收益、风险、验证和回退方式。标明决策来源：用户明确答复、此前授权覆盖、或待用户决定。不能把 Agent 的建议记录成用户确认。

用户反馈到达后先更新决策和范围；涉及需求变化时同步更新设计文档、阶段依赖及验收基线，保留变更理由。禁止通过删测试、降低阈值或移除原需求来掩盖失败。

执行循环：定位 → 记录方案 → 实施最小必要修复 → 运行失败项及相关回归 → 更新证据和问题状态 → 汇报。验证关闭后才标记问题已修复；将“代码已改但未验证”保留为待复验。

持续自检直到本阶段验收通过。遇到权限、环境、外部依赖或必需用户决定时明确阻塞。相同问题连续三轮修复仍无进展时停止盲目重试，保存每轮证据，说明剩余障碍并提供替代方案；此时不宣称达标。拿到新信息后继续闭环。

## 6. 最终验收与恢复执行

只有核心需求可追溯、必需检查通过、阻断问题关闭、文档与产物一致时才报告交付通过。风险分级以项目约定为准；无约定时将数据丢失、安全问题、核心流程失败及必需检查失败视为阻断，其他风险记录影响和处置。用户可以明确接受非阻断风险，但接受风险不能把失败的检查改成 PASS。

最终说明交付物、验收证据、仍有的限制和后续操作。不要承诺绝对无错误或未经验证的生产可用性。

继续旧项目时先读取三份文档与当前产物，恢复当前阶段、未关闭问题、已达成决策和下一步，避免从头设计或重复索取已有授权。每次结束保留足够的进度，供下一次 Agent 接续。
