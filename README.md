# 分阶段设计与交付 · Staged Project Delivery

一个通用的 AI Agent Skill，把项目推进组织为可追溯的流程：先重述需求，再创建设计文档和阶段计划；每阶段向用户汇报成果与问题，沟通后记录修复方案，持续自检并按证据验收。

适用于新项目开发、现有项目改造、缺陷修复，以及需要分阶段制作和验收的非代码项目。不绑定 Go、TypeScript 或其他技术栈。

## 核心能力

- **需求重述**：明确问题、目标用户、交付物、范围、约束、假设与待确认项。
- **设计先行**：形成业务流程、模块、接口、数据/状态、技术选择和失败恢复方案。
- **分阶段实施**：为每阶段定义输入、任务、产物、依赖和退出标准。
- **阶段汇报**：说明做了什么、优化手段、没做什么、告警、代码错误及验收结果。
- **沟通与决策记录**：区分用户明确答复、已有授权和待决定事项。
- **修复闭环**：问题定位 → 方案记录 → 实施修复 → 复验 → 更新记录 → 汇报。
- **断点续接**：从项目文档恢复阶段、未关闭问题和下一步。

## 工作流程

1. Agent 用“我理解你的需求是……”重述目标。
2. 读取现有资料，创建或更新设计文档，建立可检查的验收标准。
3. 按可独立演示和验证的交付物划分阶段。
4. 实施当前阶段，运行适用检查并保存证据。
5. 提供阶段总结，让用户纠正范围、方案和风险处置。
6. 将沟通结果写入优化设计文档，执行必要修复和回归检查。
7. 阶段达到退出标准后继续；最终核对需求、产物和验收证据。

用户要求逐阶段确认时，Agent 等待答复；已有授权继续全部阶段时，Agent 汇报后继续执行，不反复询问同意。

## 安装与使用

### 下载

```bash
git clone https://github.com/jianyunyi/staged-project-delivery.git
```

将 `skills/staged-project-delivery` 整个文件夹放到所用 Agent 支持的技能目录，保持 `agents`、`references` 和 `assets` 的相对路径。不同客户端的目录和安装入口可能不同，请使用该客户端的技能安装方式。

在支持名称调用的 Agent 中使用：

```text
请使用 $staged-project-delivery 处理这个项目：

项目目标：……
当前状态：……
技术栈与环境：……
交付物：……
限制条件：……
验收要求：……
沟通方式：每阶段完成后等我确认，再进入下一阶段。
```

没有技能安装入口时，可明确要求 Agent 读取并遵循 `skills/staged-project-delivery/SKILL.md`，保留其引用的模板文件。这不会自动为 Agent 增加工具、权限或持久记忆。

### 示例：开发新项目

```text
使用 $staged-project-delivery 开发一个 React + TypeScript 管理后台。
先重述需求，完成设计文档并拆分阶段。
设计确认前不要生成项目代码。
每阶段汇报成果、优化手段、未完成项、告警和代码错误。
```

### 示例：修复已有项目

```text
使用 $staged-project-delivery 排查并修复当前项目的 CSV 导出问题。
先读取已有设计和代码，记录复现证据及验收标准。
每阶段向我汇报，沟通后把方案写入优化设计文档再修复。
不要扩大范围，不要删除失败测试来通过验收。
```

### 示例：继续项目

```text
使用 $staged-project-delivery 继续当前项目。
先读取设计文档、优化设计文档和阶段报告，恢复未关闭问题与下一步。
按照已经确定的方案推进。
```

## 项目执行时生成的文档

| 文档 | 内容 |
|---|---|
| `project-design.md` | 需求理解、方案、需求与验收映射、阶段计划、决策变更 |
| `optimization-design.md` | 问题证据、根因、修复方案、沟通决策、修复轮次和复验结果 |
| `stage-report.md` | 每阶段成果、优化、未完成项、告警、代码错误、检查证据和下一步 |

已有同类文档时更新原文件。项目规模小时精简章节，但保留需求映射、验收证据和决策记录。文档保存位置遵循用户要求和项目规范。

## 验收与自检规则

| 检查状态 | 含义 |
|---|---|
| `PASS` | 检查实际通过，有证据支持 |
| `FAIL` | 检查实际失败 |
| `BLOCKED` | 检查被环境、权限或依赖阻塞 |
| `NOT RUN` | 尚未运行 |
| `N/A` | 对当前任务不适用，需说明原因 |

阶段状态为：进行中、待沟通、修复中、通过、阻塞。

- 实现结束不代表阶段通过；构建成功不能替代相关测试。
- 未运行或因环境问题无法运行的检查不能记为通过。
- 修复必须复验；“代码已改但未验证”保留为待复验。
- 风险接受不能将失败检查改成通过；阻断问题未解决时，不进入依赖其结果的阶段。
- 性能优化有测量时报告前后结果，没有测量时只描述预期收益。
- 不通过删除测试、降低阈值或移除需求掩盖失败。
- 同一问题连续三轮修复无进展时，保存证据并报告阻塞，拿到新信息后继续。

## 能力边界

这是 Agent 的工作流程约束，不能保证绝对无错误或无限次自动修复。验收依赖具体标准、可用环境和真实检查证据。用户的明确要求与授权优先；部署、外部写入等操作仍须遵循执行环境的权限规则。

技能源文件已完成格式校验，并用“测试依赖缺失、安全问题延期”的示例验证了阻塞报告和决策记录行为。这些验证不等同于所有 Agent 客户端的兼容性测试。
