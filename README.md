# 分阶段设计与交付 · Staged Project Delivery

版本：**0.3.0** · 许可证：[MIT](LICENSE)

一个通用的 AI Agent Skill，把项目推进组织为可追溯的流程：先重述需求，再创建设计文档和阶段计划；每阶段向用户汇报成果与问题，沟通后记录修复方案，持续自检并按证据验收。

适用于新项目、现有项目改造、缺陷修复，以及需要分阶段制作和验收的非代码项目。不绑定任何技术栈或 Agent 客户端。

## 核心能力

- **三档模式**：Lite（单份记录）、Standard（三份文档）、Full（加设计确认关卡与独立复核），开工时声明，拿不准选高一档。
- **需求重述**：问题、目标用户、交付物、范围、约束、假设与待确认项。
- **设计先行**：流程、模块、接口、数据/状态、技术选择、失败恢复；验收标准在实施前冻结，修改必须留决策记录。
- **分阶段实施**：每阶段有输入、任务、产物、依赖、退出标准；退出前重跑前序阶段的 smoke 项，防止修复破坏已通过内容。
- **编码与复验**：理解问题后优先复用已有代码、标准库与已装依赖；修复记录根因、调用方与同类路径，并复验这些路径。每个非平凡逻辑关联最小可运行检查。
- **设计边界与度量**：设计记录“有意简化与上限”；每阶段记录实现/测试/文档 diff、返工轮次和阻塞事件，缺数据明确标记。
- **问题分级**：S0 到 S3 四级，S0、S1 阻止阶段通过；区分错误、告警、风险、限制。
- **短版汇报**：对话里 15 行以内，结论与"需要你决定的事"放最前，完整内容写入阶段报告。
- **修复闭环**：定位 → 记录方案 → 修复 → 复验 → 更新记录；同一失败特征连续三轮无进展即停止并报告阻塞。
- **检查点与操作授权**：记录产物版本/哈希、验收证据和恢复步骤；不默认 commit/tag/push；已有明确授权按对象和范围沿用，未授权操作停在具体方案处。备份避免被测试自动发现。
- **无人值守兜底**：用户不在时记录假设，只做可回退的独立工作，不跨过依赖未决事项的阶段。
- **断点续接**：每份文档顶部有状态块，续接时先读状态块和未关闭问题。

## 模式与沟通方式

| 模式 | 适用 | 产物 |
|---|---|---|
| Lite | 预计实现改动 ≤3 个文件且 ≤1 小时，无架构决策，无不可逆操作 | `delivery-notes.md` |
| Standard | 多模块，2–4 个阶段 | 三份文档 |
| Full | 新项目、跨系统、涉及迁移/安全/支付/权限/对外发布 | 三份文档 + 设计确认关卡 + 高风险阶段独立复核 |

沟通方式可选"逐阶段确认"或"连续执行"。你没指定时：Full 为设计确认后逐阶段确认，Standard 为设计确认一次后连续执行，Lite 为连续执行。

## 安装与使用

```
git clone https://github.com/jianyunyi/staged-project-delivery.git
```

把 `skills/staged-project-delivery` 整个文件夹放到所用 Agent 的技能目录，保持 `references`、`agents`、`assets` 的相对路径。

- 支持 SKILL.md 约定的客户端（如 Claude Code）：放入用户级或项目级的 skills 目录，自动触发或按名称调用。具体目录和调用语法以该客户端文档为准。
- 读取 `agents/openai.yaml` 的客户端：该文件提供名称和默认提示词，其他客户端会忽略它。
- 不支持技能目录但支持仓库指令的客户端：将根目录 [AGENTS.md](AGENTS.md) 的规则合并到目标项目已有指令文件，保留原规则；不要覆盖已有文件。若客户端也不支持 AGENTS.md，显式要求读取该文件。精简版不包含完整模板和例子，需要完整流程时再提供技能目录。
- 没有技能安装入口时：明确要求 Agent 读取并遵循 `SKILL.md`，同时提供 `references/` 下的文件。这不会为 Agent 增加工具、权限或持久记忆。

调用时说明目标、当前状态、环境、交付物、限制、验收要求和沟通方式，例如：

```
请使用 staged-project-delivery 处理这个项目：
项目目标：……
当前状态：……
技术栈与环境：……
交付物：……
验收要求：……
沟通方式：设计确认后每阶段等我确认。
```

修复已有项目、继续旧项目的写法：

```
使用 staged-project-delivery 排查并修复 CSV 导出问题。先读取已有设计和代码，记录复现证据和验收标准。不要扩大范围，不要删除失败测试来通过验收。
```

```
使用 staged-project-delivery 继续当前项目。先读三份文档的状态块和未关闭问题，按已确定的方案推进。
```

## 项目执行时生成的文档

| 文档 | 内容 |
|---|---|
| `project-design.md` | 需求理解、方案、需求与验收映射（含 smoke 标记）、阶段计划、决策变更 |
| `optimization-design.md` | 问题证据、级别、根因、修复方案、沟通决策、修复轮次与复验结果 |
| `stage-report.md` | 每阶段结论、待决策事项、成果、优化、未完成项、告警、错误、检查证据 |
| `delivery-notes.md` | 仅 Lite：上述内容的合并精简版 |

已有同类文档时更新原文件。每份文档顶部有状态块，已关闭阶段的细节归档到文末"历史"。

## 验收与自检规则

| 检查状态 | 含义 |
|---|---|
| `PASS` | 检查实际通过，有证据支持 |
| `FAIL` | 检查实际失败 |
| `BLOCKED` | 被环境、权限或依赖阻塞 |
| `NOT RUN` | 尚未运行 |
| `N/A` | 不适用，需说明原因 |

| 问题级别 | 含义 | 对推进的影响 |
|---|---|---|
| S0 | 数据丢失/损坏、安全漏洞、核心流程不可用、必需检查失败 | 阶段不得通过，依赖阶段不得开始 |
| S1 | 主要功能缺陷或明显回归 | 阶段不得通过；用户可明确接受并记录，检查状态仍为 FAIL |
| S2 | 次要缺陷 | 记录，可延期 |
| S3 | 体验、风格、文档瑕疵 | 记录 |

- 实现结束不代表阶段通过；构建成功不能替代相关测试。
- 未运行或因环境问题无法运行的检查不能记为通过。
- 风险接受不能把失败检查改成 PASS。
- 性能优化有测量时报告前后结果，没有测量时只描述预期收益。
- 不通过删除测试、降低阈值或移除需求掩盖失败。
- 同一失败特征连续三轮修复无进展时，保存证据并报告阻塞，拿到新信息后继续。

## 能力边界

这是 Agent 的工作流程约束，不能保证绝对无错误或无限次自动修复。独立复核依赖客户端是否支持子 Agent 或新会话，不支持时报告会标明"未独立复核"。验收依赖具体标准、可用环境和真实检查证据。用户的明确要求与授权优先；部署、外部写入等操作仍须遵循执行环境的权限规则。

## 评测与版本维护

三例可执行评测、原版与新版产物及维护者评分见 [evals](evals/README.md)。每次改动技能后重新运行三例，功能检查与流程评分分别比较；CI 校验技能哈希与评测版本一致，复跑产物功能测试。CI 不会自动调用模型，fresh-agent 执行与流程审查是明确的独立步骤。版本号保存在 VERSION；改变行为时更新版本和对应评测证据。
